# Story Oracle 手机应用：路线工作台与 TASKOW 风格 UI 重构设计

## 1. 目标

将剧情助手从“会话区的另一套气泡”收敛为独立的剧情路线工作台：

- 第二轮及后续大纲生成后，必须在当前视觉范围内可见；
- 用户消息与助手回复保持完整可见，不能被空态或状态栏覆盖；
- 每条路线是独立、可操作、可追踪的工作项；
- 启用路线在顶部纵向显示，长标题可读；
- 视觉参考 TASKOW：白色页面、深蓝主操作、灰阶辅助文字、弱化分隔、无装饰性描边、强垂直呼吸感；
- 与普通会话区形成明确产品区分，不复制普通聊天气泡的排列和视觉语言。

## 2. 现状诊断

### 2.1 第二轮大纲可见性

当前 `appendStoryOracleTurn()` 会将新用户消息和助手消息追加到当前模式历史，并把当前响应解析出的计划追加到既有 `currentScope.plans`。因此数据层没有明显的“每轮覆盖旧计划”语句。

但当前可见性存在三个断点：

1. 只有响应中成功解析出 `<StoryPlan>` 时才会新增路线；普通文本虽然显示为“回答已保存”，却不会产生路线卡；
2. 路线通过 `sourceMessageId` 与助手消息绑定，绑定失败或历史计划没有对应消息时才进入末尾兜底区域，用户无法判断它属于哪一轮；
3. 页面状态只表达保存结果，不表达“本轮解析到几条路线”，导致用户误以为保存即代表路线已进入视觉区。

### 2.2 当前 UI 问题

- `.pm-story-oracle-message` 与 `.pm-bubble` 直接复用会话区语言，页面缺少独立工作台层级；
- 活动路线横向胶囊会截断长标题，无法确认当前启用了什么；
- 计划操作区三按钮等分铺满，主次不分，删除使用大面积危险色；
- 状态通知占据固定垂直空间，且与内容区竞争；
- 空态说明被当作消息列表内容，造成“输入文字”类文案顶在顶部；
- 计划信息、消息、当前活动线路、输入区缺少明确的页面级分组。

## 3. 交互与数据可见性方案

### 3.1 生成结果收据

每次参谋请求完成后，页面顶部只显示短暂收据，不显示泛化的“已保存”：

- 解析到路线：`本轮生成 2 条路线，已加入路线工作台`；
- 没有解析到路线：`本轮已保存，但没有识别到可操作路线`；
- 解析失败：`本轮文本已保存，路线格式未识别`；
- 保存失败：明确显示保存失败，不伪装成功。

收据自动消失，不进入消息历史，不占据永久布局。原型阶段可采用定时消失；正式实现需确保定时器随页面销毁清理。

### 3.2 多轮路线展示

页面内容顺序固定为：

1. 页面标题区；
2. 活动路线区（仅有启用路线时显示）；
3. 本轮收据（仅有状态时短暂显示）；
4. 路线工作台：按生成时间/稳定 order 倒序或分组显示最新路线；
5. 剧情助手消息流：用户问题和助手说明；
6. 底部输入区。

每条路线必须带来源轮次标识或生成时间的可读短标签，避免第二轮路线与第一轮混淆。用户要求“看得到第二轮”，因此新生成路线默认插入路线工作台的当前可见区域，不只追加到滚动底部。

### 3.3 解析与保存契约

- `StoryPlan` 仍是唯一可操作路线来源；普通文本必须保留在消息流，但不能伪装成路线；
- 解析结果至少保存：title、goal、seed、why、pace、sourceMessageId、createdAt、order、enabled；
- 生成后页面应使用本次响应解析结果确认新增数量，而不是只依赖“保存成功”；
- 不改变 `STORY_ORACLE_STORE_VERSION`，不删除旧计划，不覆盖历史路线；
- 若第二轮没有路线，UI 必须明确显示“已保存但未生成可操作路线”，避免用户继续误判为视觉丢失。

## 4. 页面信息架构

### 4.1 顶部标题区

参考 TASKOW 的 `Tasks / Create Checklist / New Tasks`：

- 左侧返回图标；
- 中央标题“剧情参谋”或“剧情聊天”；
- 右侧工具入口，保持图标按钮，不放多余说明文字；
- 标题区白底、无底部厚重边框，仅用空间和层级分隔。

### 4.2 路线工作台

将原 `.pm-story-oracle-plan-bubble` 改为工作项布局，而不是聊天气泡：

- 页面宽度 100%，内容左右留白；
- 每条路线以留白、标题字重、浅色状态标记区分，不依赖完整描边；
- 标题可换行，目标为主信息；
- 起始迹象、契合点、推进速度为次级信息，默认紧凑但不截断关键文本；
- 操作顺序：`开始引导/停止引导` 为唯一主操作，`继续讨论` 为次操作，`删除线路` 为低强调危险操作；
- 删除线路使用危险色文字或细弱危险色状态标记，不使用大面积红色背景；
- 活动状态通过主色标签、标题旁状态文字和置顶区域共同表达。

### 4.3 活动路线区

- 采用纵向列表，每条活动路线独占一行；
- 标题允许自然换行，禁止 ellipsis 截断；
- 每行显示状态与完整标题，必要时显示推进速度；
- 不使用横向滚动作为主要阅读方式；
- 无活动路线时不渲染空容器。

### 4.4 消息流

- 用户问题必须显示为右侧、深蓝底、白字的独立消息块；
- 助手说明显示为左侧、白底或页面表面色的阅读块；
- StoryPlan 正文从助手说明中剥离，路线工作项独立显示；
- 空消息时不渲染“输入问题……”类伪消息；输入提示只能存在于 textarea placeholder；
- 消息流与路线工作台使用不同间距和层级，不能让路线卡看起来像一条助手气泡。

### 4.5 底部输入区

参考 TASKOW 创建页的明确主操作：

- 输入区保持白底或浅表面色；
- 文本输入区域有足够高度和留白；
- 发送按钮使用深蓝主色，保持唯一主操作；
- 工具、世界书、模式切换使用低强调图标/文字入口；
- 不在输入区堆叠多个强色按钮。

## 5. 视觉规范

### 5.1 颜色

- 页面背景：`--pm-color-surface-page`；
- 内容分组：`--pm-color-surface-card` 或现有表面语义；
- 主操作：`--pm-color-accent` + `--pm-color-on-accent`；
- 正文：`--pm-color-text-primary`；辅助信息：secondary/tertiary；
- 删除：`--pm-color-danger` 仅用于文字、图标或细弱状态表达；
- 禁止新增裸色、渐变和高饱和装饰背景。

### 5.2 形态

- 默认无完整描边；只有输入控件、焦点环和必要的分组边界允许保留现有语义描边；
- 不使用重阴影；浮层继续使用现有 floating shadow；
- 不给每个字段套圆角卡片；用留白、字重和分组间距建立层级；
- 保留现有 token，不新增单组件全局 token；
- 视觉节奏优先使用 space-2/space-3/space-4，避免手调像素。

### 5.3 TASKOW 素材吸收范围

吸收：

- 白底大留白；
- 中央标题与简单返回入口；
- 标签/分段选择的轻量状态；
- 深蓝唯一主按钮；
- 空态使用图形、标题和短说明的三层结构；
- 信息按垂直层级排列，而不是堆成气泡。

不吸收：

- TASKOW 的业务文案、任务字段、图形资源直接复制；
- 固定图片尺寸或与手机壳不匹配的绝对定位；
- 与当前 phone-mode 不兼容的字体、颜色和圆角硬编码。

## 6. 功能修复实施边界

允许修改：

- `src/story-oracle-model.js`：路线速度/来源轮次/解析收据所需的最小字段透传；
- `src/story-oracle.js`：生成结果收据、路线排序/当前轮可见性、消息与路线工作台布局、状态提示生命周期；
- `styles/core.css`：仅限 `.pm-story-oracle-*` 组件族；
- `scripts/check-contracts.mjs`：同步可机器验证的 UI/输出契约；
- `scripts/check-story-oracle.mjs`：同步路线累计与无路线响应语义；
- `index.js`：由构建生成，不手工编辑。

禁止修改：

- 主聊天消息、世界书正文、角色资料和其他模块 store；
- `STORY_ORACLE_STORE_VERSION`，除非先获得迁移设计批准；
- 普通聊天、社区、日历和今日风向的视觉规则；
- 宿主 API 参数和扩展提示命名空间；
- 本机代理、认证、推送配置或诊断日志。

## 7. 风险

- 第二轮响应可能只是普通文本，不能把它误报为路线生成成功；
- 路线与消息绑定变化可能造成历史路线重复或错位；
- 自动消失通知若未清理定时器，可能在页面切换后重绘旧页面；
- 无描边设计若层级不足，会导致路线项与页面背景融合；需用间距、字重、表面色和主操作状态补足对比；
- 活动路线纵向展示可能压缩消息可视高度，需要保留列表滚动和输入区固定可见；
- TASKOW 图片是视觉参考，不是当前宿主的尺寸和 token 契约，不能照搬绝对值。

## 8. 验证方式

原型阶段：

- 第一轮生成两条路线，确认两条均可见；
- 第二轮再生成两条路线，确认第一轮和第二轮均保留，且第二轮出现在当前视觉范围；
- 第二轮无 `<StoryPlan>` 时，确认普通回复可见并明确显示“未识别到路线”；
- 启用一条长标题路线，确认顶部逐行显示且完整换行；
- 确认用户输入消息可见；
- 确认通知自动消失；
- 确认删除线路为低强调危险样式；
- 确认页面与普通聊天区有明显结构差异。

生产阶段补充：

- 亮/暗主题、320px 窄屏、键盘焦点、刷新恢复、聊天切换、取消请求、存储失败、宿主注入和真实浏览器 DOM；
- 构建、语法、契约、专项测试、差异检查和独立验收。

## 9. 设计自查

这版设计比当前实现可靠，但仍有一个必须在实施前锁定的产品取舍：第二轮路线是否按“最新生成在上”排序，还是严格按时间顺序保留。前者更符合“当前视觉范围”，后者更符合历史回溯。建议工作台采用“最新生成在上”，消息流仍保持时间顺序；如果助手要求严格时间顺序，需要在实施前确认。
